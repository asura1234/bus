# Grok provider assessment

Date: 2026-10-22. Historical investigation baseline: read-only assessment before G0. Subsequent approved scaffold work and lane interfaces are recorded in [lanes.md](lanes.md).

**Verdict: feasible for both worker and room orchestrator; medium overall effort, with substantial lifecycle QA.** Grok Build 1.0.5 already has native lifecycle hooks, stable session IDs, persisted transcripts, interactive and headless modes, and documented background-command completion wakes. It does not require a screen-only reply adapter. **The live test of an idle session automatically starting another model turn is PENDING, not passed**: authentication is unavailable; verification remains pending because Grok is not signed in. The first version can orchestrate using Bus's existing durable worker-reply notifications without depending on that native wake.

The closest adapter to copy is **Claude for hook semantics and final-reply capture**, combined with **Cursor for project settings/consent and first-message orchestrator prompt installation**. Keep Grok's camelCase payload decoding separate; neither existing decoder is a drop-in replacement.

## Installed Grok: capabilities and limits

### Help, config and storage

`grok [OPTIONS] [PROMPT] [COMMAND]` starts the interactive TUI; a positional prompt starts interactive work. It supports model/reasoning selection, permission modes, allow/deny rules, cwd, explicit UUID creation/resume/fork, extra system rules, system-prompt override, fullscreen/minimal/inline modes, debugging and a custom leader socket. `--no-leader` and `--no-auto-update` are accepted hidden options; an isolated `inspect --json` run with both exited zero. Do not assume every similarly named headless flag works in the interactive TUI.

Noninteractive entry points are native: `-p/--single`, `--prompt-file`, or `--prompt-json` process one prompt and exit; output can be plain, JSON, ACP-derived NDJSON, or Messages-style NDJSON. `grok agent stdio` is a long-lived ACP JSON-RPC endpoint with session/new, session/prompt, updates, permissions and session loading. It supports `--no-leader`; serve/relay variants also exist. Headless or ACP support is useful future infrastructure, but replacing Bus's interactive PTY architecture with ACP is a larger separate project.

Docs: `~/.grok/docs/user-guide/05-configuration.md`, `14-headless-mode.md`, `15-agent-mode.md`, `17-sessions.md`. Config discovery includes user/project/managed layers and compatibility sources. `GROK_HOME` redirects storage; redirecting it in production also moves sessions/auth/config, so it is not a harmless per-launch settings trick.

Local sessions are long-lived and persisted. The offline probe created real session directories with summary, updates and raw history; shutdown printed `grok --resume <UUID>`. Resume restores the conversation, not surviving operating-system background processes. A restart must reconcile pending Bus work through durable Bus state, not assume a sleeping shell survived.

### What was observed on screen

The real binary displayed the welcome/login surface, boxed `❯` composer, `/hooks` modal, and `/session-info` modal with Context usage / Usage limit tabs. `/hooks` showed the scratch hook source; Session info exposed session ID and current model. A deliberately invalid, non-secret placeholder API key was used only inside the network-denied sandbox to open local views; “Logged in with API key” is UI evidence, **not authenticated model access**. No model request or coding task was submitted.

The installed keyboard guide describes permission rows (allow once, reject, optional persistent scope, always-approve), question tabs, checkboxes, a free-text row, focus parking and cancel panels. The existing Bus Grok manifest was authored from **0.2.101**, not 1.0.5. Its `┃ N (○)` examples are useful parser hypotheses only. Actual 1.0.5 permission/trust/question rendering and narrow/wrapped layouts require new captures; we did not manufacture those as live fixtures.

### Hook details that change the estimate

The captured real hook payloads use `hookEventName:"session_start"`, camelCase `sessionId`, `source:"new"`, and later `transcriptPath` pointing to updates.jsonl. Shutdown emitted both session_end and stop with `reason:"shutdown"`; that Stop has **no promptId or answer**, so a naive Claude-shaped decoder would misclassify it.

The binary-matching hook guide states:

- Turn-scoped events carry `promptId`; child events can carry `subagentType`. Use IDs/provenance, not event timestamps, to correlate callbacks.
- Stop can be invoked repeatedly as other stop gates continue a turn. Even a completed Stop handler can be followed by cancellation. At the continuation cap a final Stop may be absent. The idle-prompt Notification is a delayed session-level backstop, roughly a minute after idle, and can have no promptId. It cannot safely name a request's reply by itself.
- `lastAssistantMessage` is capped at 32,768 characters. API failure and cancellation events are separate; their assistant text must not become a successful answer.
- Hook execution can fail open, be disabled, or be skipped for lack of project trust. Treat missing observation as an explicit failure/pending state; do not resubmit uncertain work.

These are reasons for a dedicated completion/transcript resolver and tests, not for a large provider-framework rewrite.
