# Build the room-bound workflow orchestrator harness

- Status: ready-for-review
- Created: 2026-09-14
- Author: dylanliu
- Branch: master
- Base commit: 057adf8d773a8417825844801588634c7656d241
- Working-tree prerequisite: the ordered-recipient and prompt-grouped-history change listed as Task 0

## Goal

Add a durable, room-bound, DeepSeek-backed orchestrator to Bus that lets a human describe requirements, load or draft versioned Markdown workflows whose topology is an embedded Mermaid Agentflow graph, approve a locked goal and visible execution plan, and then delegate, monitor, unblock, question, replace, and converge coding agents without the orchestrator performing the technical work itself.

## Non-goals

- Do not embed Codex, Claude Code, Cursor, OpenCode, Pi, or another coding-agent harness as the orchestrator.
- Do not hard-code `review-plan`, `review-pr`, `address-review-comments`, best-of-N, software engineering, or any other domain workflow into the harness. Those remain capabilities of participating agents and instructions in repository-owned workflow Markdown.
- Do not give the orchestrator shell access, source-control access, test execution, project-file writes, arbitrary keyboard injection, arbitrary source search, or an editor tool.
- Do not allow a workflow, room message, repository file, agent reply, or model output to expand the orchestrator's compiled capability boundary.
- Do not automatically start work when the user selects or talks to `@Orchestrator`; execution begins only after an exact proposed goal/to-do revision receives explicit human approval.
- Do not include the orchestrator in `@All` or silently fan ordinary room prompts out to it.
- Do not implement the future best-of-N skill. A workflow may reference it, and the orchestrator may assign it to an agent only when that capability is available.
- Do not generate Appium or other scripted UI tests as a default acceptance mechanism. A workflow may delegate computer-use acceptance to a capable coding agent.
- Do not add another orchestrator model/provider in this change. The model selector is future-ready but initially exposes only DeepSeek V4.1 Flash (internal enum `DeepSeekV41Flash`, current wire model `deepseek-flash`).
- Do not stream or display model reasoning. The first provider adapter uses complete, non-thinking Chat Completions responses to minimize partial-state and recovery complexity.
- Do not automatically publish, commit, push, merge, delete agents, delete worktrees, or promote temporary workflows.
- Do not execute Python, JavaScript, shell, Mermaid click handlers, workflow-supplied plugins, or any other arbitrary code from a workflow file. Mermaid describes topology and typed metadata; the Rust harness executes only its closed capability set.
- Do not build a second general-purpose workflow language, visual editor, or complete Mermaid renderer. Support a pinned, fail-closed Bus profile of Mermaid Agentflow inside Markdown and compile it to the existing typed orchestration model.
- Do not guarantee that semantic output filtering can inspect an LLM's private reasoning. Enforce the boundary through withheld technical context, restricted tools, typed/provenanced outward actions, and fail-closed policy checks.

## Requirements

1. Bus Settings contains an **Orchestrator agent** section with a model dropdown and masked API-key editor. The only initial model label is `DeepSeek V4.1 Flash`, represented by internal enum `DeepSeekV41Flash` and mapped only at the provider boundary to the current documented wire model `deepseek-flash`. Task 4 must re-check the official model list before pinning the adapter and fail visibly if that name has changed; runtime discovery never silently substitutes a different model.
2. The API key is stored only in a private Bus credential file beside the shared registry settings file (or inside the explicit `BUS_DATA_DIR` root), never in `BusState`, UI snapshots, room history, diagnostics, tracing fields, panic/debug output, workflow files, or agent prompts. A monotonically changing credential generation/digest is revalidated from that shared file before every model call, so saving or clearing affects the current session immediately and every other live session before its next call. A failed credential write leaves the prior file bytes and active generation unchanged.
3. Configuring a key makes one logical orchestrator available in every existing and future room. Clearing the key disables new model calls and preserves each room's conversation, proposal, goal, to-do, inquiry, and recovery state for later re-enablement.
4. The recipient picker renders a dedicated `Orchestrator` entry first, then a non-selectable blank/divider row, then `All`, then coding agents. Selecting `All` changes only coding-agent recipients. An orchestrator recipient may be combined manually with specific coding agents, but is never selected by `All`. Drafts and prompts persist one ordered `RoomRecipient` sequence containing `Orchestrator` and `Agent(AgentId)` variants, so a mixed send preserves the user's exact `@` order without fabricating a terminal agent.
5. Sending a message to `@Orchestrator` starts or continues an ordinary conversation. It may clarify requirements, report status, or propose coordination actions, but it cannot transition a workflow into execution merely because it was addressed.
6. The orchestrator journal owns structured room requirements, goal, non-goals, and goal-lock revisions. Human edits and model-proposed edits to an unlocked brief are serialized as actor events; later sequence wins and every proposal cites the exact resulting revision. Approval locks the exact brief and to-do proposal hash. An edit request against a locked brief is recorded as a pivot draft and cannot mutate the active lock; affected work pauses until the new revision is approved.
7. The room view removes the notes editor and replaces that entire seeded F3 header surface with separate Goal and Non-goals fields inside the existing eight-row budget, including their draft/locked state. F3, mouse selection/hit targets, short-terminal focus behavior, help, and usage copy are rebound to those fields. Existing `Room::notes` remain durable for state compatibility and are never presented as the goal source or an editable second writer. When legacy notes are non-empty, the right panel exposes a clearly labeled, collapsible, read-only and selectable **Legacy notes** block; empty notes render no block. Locked fields are read-only until a pivot revision is approved, and coding-agent skills consume the locked values without redefining them.
8. When the orchestrator proposes work, a right-side room column shows the to-do list, dependencies, proposed agent role/family/model/effort, assignment owner, current state, blockers, and completion evidence. The panel contains an explicit approve/revise action; no agent is created and no work message is sent before approval is durably recorded.
9. On narrow terminals the room remains usable: the to-do panel becomes an explicit alternate/collapsible room view with a visible proposal/status indicator rather than reducing the composer or history below their existing minimum usable geometry. Opening a coding-agent terminal continues to use the existing terminal surface.
10. Workflows are ordinary UTF-8 Markdown discovered from human-registered room roots and the distinct canonical worktree roots represented by room-agent PWDs: `.bus/standard/*.md` for developer-owned workflows and `.bus/temp/*.md` for orchestrator-authored temporary workflows. Each file has YAML frontmatter with `bus-workflow: 1`, identity/description, and bounded run policy; exactly one fenced `mermaid` block beginning with the Bus profile's pinned Mermaid 12.0.0 `agentflow-beta` grammar; and optional Markdown instruction/reference sections addressed by stable graph IDs. Root IDs are harness-issued and visible in proposals. Duplicate names with identical content hashes coalesce; differing content requires explicit root disambiguation. A rootless room may converse and draft requirements, but proposal approval/agent launch stays `needs_human` until the human registers a root or creates an agent with a valid PWD.
11. Workflow Markdown and Mermaid are declarative instructions/data, never executable code or an authority source. A strict Rust compiler accepts only the documented Bus Agentflow profile, resolves same-file instruction references, and emits a canonical typed `CompiledWorkflow`. The profile admits only supported containers, task/input/decision/refdoc/action shapes, sequence/reference/failure edges, bounded cycles, and a closed metadata vocabulary for skills, roles, family/model/effort selection, lane count, isolation, outcome contracts, retries, and budgets. It rejects tool/connector execution in v1, presentation directives, click/link/HTML behavior, duplicate/unreachable IDs, dangling references, ambiguous branches, unbounded cycles, unsupported shapes/edges, unknown metadata, and any requested capability outside the harness registry. Upstream Mermaid warnings relevant to execution are errors in Bus.
12. The harness snapshots the exact workflow source hash, Bus workflow/profile version, compiler version, canonical compiled-graph hash, and resulting proposal hash before approval. The UI presents the compiled graph/to-dos rather than trusting labels alone. An approved run executes the stored compiled graph without re-reading or reinterpreting the file; source, grammar, or compiler changes affect only a newly compiled proposal and require a new exact approval.
13. The orchestrator may create and atomically update files only below the selected canonical `.bus/temp/` directory. Its binary-owned `workflow-writing` skill may load the pinned schema and examples, author or revise a temporary workflow, request deterministic compile diagnostics, and propose the resulting graph. It cannot directly write `.bus/standard/`. Promotion or replacement of a standard workflow creates a durable pending-promotion record and visible diff; only an explicit human UI/control action bound to root, path, old hash, new hash, compiled graph hash, and diff hash can authorize the harness to perform that write once. Natural-language or model-issued approval is rejected.
14. The harness-level system contract and binary-owned `workflow-execution` skill define the orchestrator as a domain-neutral process owner. The skill may explain a proposal, report sitrep, route inquiries, and select only harness-enumerated recovery transitions when execution diverges. The Rust executor, not the skill or model, performs the routine dispatch/wait/join/advance loop without model calls. Both skills are embedded read-only harness resources, cannot be shadowed by repository files, and must delegate implementation analysis and technical decisions to coding agents.
15. The context builder gives the model the requirements, locked brief, approved workflow snapshot, current to-dos, dependencies, assignments, agent statuses, open blockers/permissions/inquiries, decisions/pivots, and a bounded recent coordination conversation. It does not preload source, diffs, complete terminal transcripts, test logs, or other agents' private technical investigations.
16. Read-only workspace access is room-scoped and intentionally high-level. `workspace_outline` exposes names/types only, at depth 2, at most 512 entries and 64 KiB, from harness-issued root IDs. `read_coordination_document` accepts only root-level `README.md`, `AGENTS.md`, `CLAUDE.md`, `CONTRIBUTING.md`, `ARCHITECTURE.md`, `.bus/README.md`, or an already-selected workflow snapshot, at 32 KiB per file and 64 KiB per turn. A shared resolver uses relative normalized paths, no-follow/handle-based opens where supported, post-open identity checks, and fail-closed traversal, symlink/junction/reparse, case-variant, hidden/credential/VCS, cross-root, oversized, arbitrary-glob, and replacement checks.
17. Every human-visible orchestrator response is emitted through a typed response variant: structured coordination summary over cited coordination object IDs, bounded exact excerpt of cited coding-agent reply IDs from the same room/run, or a structured human-judgment request. Rust validates IDs, room/run ownership, excerpt membership, caps, and allowed coordination fields; unverifiable technical claims cannot become evidence, decisions, or tool inputs. The fixed system contract still instructs the model to delegate technical questions, but semantic detection of technical prose is explicitly best-effort and does not pretend to be a deterministic CI gate.
18. The orchestrator can propose room-agent profiles, send assignment-scoped room messages, inspect bounded permitted agent output and status, register interruptible reply wake conditions, maintain assignments, and update to-do state through capability-checked versions of the same Bus operations exposed by the developer/test CLI. Approved initial agents/messages and every ordinary graph transition are created by the deterministic harness executor from the locked compiled graph, not by an unrestricted model tool or repeated model interpretation. The orchestrator never shells out to the CLI or accepts a model-supplied room ID, root, arbitrary PWD, or next-node identifier outside the executor's enumerated legal transitions.
19. Agent launch specifications persist a harness-issued `root_id`, provider, model, effort, role, assignment, and originating workflow/run IDs. The selected root/PWD is visible before approval. A provider capability table translates supported effort levels into reviewed launch options and fails visibly when a requested root/model/effort combination cannot be expressed; it never silently downgrades effort or inserts unrestricted launch arguments.
20. The orchestrator chooses effort from a small rubric based on proposed task complexity, while a workflow may set a minimum or exact level. The proposed model and effort are visible before approval. Increasing effort for an already-running agent requires an explicit replacement/handover rather than mutating an opaque live coding session.
21. Workflow isolation requirements are represented in the compiled graph and proposal. While an isolation group is open, lane bodies/tails are stored durably but withheld from orchestrator model context, peer prompts, `get_room_state`, `read_agent_tail`, wake results, and every other model-visible tool result; the model sees only runtime status, reply IDs, evidence digests, and a Rust-parsed lane outcome. Every harness-constructed isolated-lane assignment requires a final bounded envelope with `state = complete | needs_input | blocked` and evidence references. Rust validates only the final envelope and exposes its typed state without the reply body. `needs_input`, `blocked`, missing/malformed envelopes, or invalid evidence set the run to `needs_human` and project the correlated reply directly to the human; they never count as completion. Convergence may open only after every required lane has a valid `complete` outcome. Peer content becomes model-visible only after the journal records that transition. If required family diversity or lane count is unavailable, it asks the human rather than weakening the workflow silently.
22. The orchestrator remains conversational during an approved workflow. A sitrep is generated from durable to-do/agent state. Waiting registers a durable reply/deadline subscription and ends the current step; an agent reply, deadline, or queued human message wakes the actor with metadata only, and human input takes the next bounded model turn. A side inquiry is routed to the agent owning the relevant task and stored separately from workflow dependencies. If that owner belongs to an open isolation group, the harness projects the correlated reply directly to the human by reply ID without putting its bytes into a provider request; the model may acknowledge only the status/reference. Outside isolation, the normal verified-excerpt relay is available. The main workflow changes only when the human explicitly requests a pivot.
23. Agent supervision distinguishes working, blocked, idle, unavailable, timed out, repeated-failure, and suspected-divergence states. The orchestrator may answer process questions from the locked brief/workflow, provide an allowlisted safe permission, ask another agent for technical judgment, or escalate; it cannot use its own technical guess to settle a substantive implementation disagreement.
24. Permission handling never exposes raw `agent.send_keys` to the model. A provider-specific parser binds a recognized permission prompt to terminal identity, a real monotonically changing output revision/digest, action category, and normalized paths. A new server-side approve-once operation atomically rechecks those values and writes the fixed response in one handler. The initial automatic allowlist is limited to recognized provider prompts for filesystem read, edit, or create actions wholly inside the assigned registered PWD; shell-command, network, package install, Git publication/history rewrite, deletion, credentials, hidden/VCS paths, unknown, stale, or out-of-root prompts always require the human.
25. A suspected hallucinating, looping, or incoherent coding agent can be proposed for retirement without erasing its transcript or worktree. Retirement/replacement requires either an exact human-approved proposal revision or an unused replacement budget/profile already visible in the approved proposal. The harness never closes a `Working` terminal, waits for an explicit safe/idle or human-approved stop boundary, confirms closure before replacement, builds a handover from trusted orchestration state and clearly marked unverified claims, and transfers ownership only after the replacement receipt is durable. Retired agents remain visible in history but are excluded from `All`, recipient selection, direct sends, and assignment.
26. Each room has a serialized orchestrator actor running off the existing Bus coordinator thread. Model calls and waits never block the 500 ms delivery/status loop or rendering. Human messages are queued with priority at the next model boundary while independent coding-agent assignments may continue in parallel.
27. A versioned append-only private journal is the sole authority for accepted orchestrator conversation, brief revisions/locks, proposals, approvals, operations, dispatches, inquiries, handovers, decisions, checkpoints, and failures. `BusState` owns rooms, terminal agents, coding-agent delivery, and the durable inbox of submitted prompts marked for the orchestrator. The actor idempotently appends `HumanPromptAccepted(prompt_id)` before advancing a persisted inbox-consumption watermark; startup replays every marked prompt past that watermark and journal deduplication makes an unacknowledged replay safe. `BusSnapshot` carries the pending inbox plus a bounded journal-derived projection and watermark. Human brief edits route through the actor. Orchestrator effects use journal intent/approval fsync, coordinator effect/receipt, journal result fsync, then snapshot publication; inbound prompts use coordinator prompt fsync, idempotent journal acceptance fsync, then coordinator watermark fsync. Crash tests cover every boundary for orchestrator-only and mixed-recipient prompts.
28. State-changing tool intent is synced before execution and completed with a durable result. Deterministic operation IDs prevent duplicate messages/agents after retry or restart. Ambiguous outcomes enter reconciliation and inspect authoritative Bus state/history instead of resending blindly.
29. Context checkpointing never rewrites authoritative requirements, locked goal/non-goals, workflow source/profile/compiler/compiled-graph/proposal hashes, to-do identities, approvals, decisions, or operation receipts. A test that performs at least ten synthetic compaction/checkpoint cycles must preserve those values exactly while discarding old technical chatter.
30. Provider retries are owned by one layer, bounded, cancellable, and limited to known pre-admission transport failures and retryable DeepSeek statuses. `stop` is accepted only for a complete text response, `tool_calls` only for complete validated calls, `length` is truncation, `content_filter` is a policy failure, and provider-returned `insufficient_system_resource`/`aborted` are bounded retryable completion interruptions before any tool execution. A locally cancelled HTTP request is a distinct runtime `Cancelled` outcome and is never decoded or retried as a provider finish reason. Unknown finish reasons, unexpected `reasoning_content`, authentication, billing, invalid request, schema failure, ambiguous side effects, and exhausted retries become actionable room state. No partial or truncated tool call is executed.
31. Restart, credential removal, room deletion, and application shutdown cancel in-flight HTTP requests and agent waits. Restart appends recovery state for interrupted turns, reconciles unresolved operations, and resumes only already-approved work from its stored compiled graph; an unapproved proposal stays unapproved.
32. The developer/test control surface can register a room root, send to `orchestrator`, inspect the brief/proposal/run/to-do/inquiry/promotion state, validate/compile a workflow, approve or revise an exact proposal, approve/reject an exact workflow promotion, and wait for an orchestrator turn using JSON responses and caller-provided request IDs. This deterministic surface is used for integration tests; API keys are never accepted as command-line arguments.
33. Initial repository-owned examples demonstrate the generic mechanism with review-plan, review-PR convergence, and plan execution workflows. Each example uses the pinned Markdown plus Mermaid Agentflow contract, references coding agents' installed skills, and contains no extra harness authority. Canonical `skills/` documentation uses an orchestrator-approved locked room brief when one is supplied in the dispatch; standalone use continues to derive Goal/Non-goals from the plan/user request. No coding skill creates, unlocks, or rewrites an existing room lock.

Local Ralph telemetry showed UI loops dominated recorded validation time, supporting computer-use delegation instead of generated Appium tests.

As re-verified on 2026-09-14, DeepSeek [Models & Pricing](https://api-docs.deepseek.com/quick_start/pricing/) says to use `deepseek-flash`, identifies its served version as DeepSeek-V4.1-Flash, and labels `deepseek-v4-flash` a retired legacy name; [GET /models](https://api-docs.deepseek.com/api/list-models) and the [Chat Completions request enum](https://api-docs.deepseek.com/api/create-chat-completion/) also list `deepseek-flash`. ## Proposed design

### Authority and component boundary

Keep terminal agents and their delivery state unchanged. Add a separate logical `OrchestratorSession` keyed by `RoomId`; do not add a fake DeepSeek variant to the terminal `Provider` enum or fabricate terminal identities.

```text
human room message / agent event
              |
              v
     room orchestrator actor -----> context projection
              |                           |
              |                      DeepSeek adapter
              |                           |
              +<---- typed action/tool ---+
              |
      compiled capability policy
              |
      durable operation intent
              |
   Bus commands / workflow store / UI projection
```

The fixed system contract is compiled into the binary (for example with `include_str!`) and always precedes workflow and room content. It states the PMO role, coordination actions, technical-delegation rule, provenance rule, goal/approval protocol, and non-expansion rule. Workflow text and all model-visible external content are delimited and labeled untrusted. Tool schemas omit shell, project write, Git, tests, arbitrary keys, arbitrary room selection, and arbitrary roots. The policy receives room/root capabilities from Rust and may only reduce them.

Do not render arbitrary assistant final text directly. The model must use one of three typed response variants: a coordination summary over allowlisted structured fields and cited coordination-object IDs; an exact, length-capped excerpt whose bytes are verified against cited coding-agent reply IDs in the same room/run; or a structured human-judgment request. Mutating actions are always tools and are validated independently of the model-facing JSON schema. Rust mechanically validates IDs, ownership, fields, excerpts, and caps; the system contract tells the model to delegate technical questions, but semantic classification of prose is best-effort rather than a security claim. If the provider emits final text or a disallowed action, append a policy event and make one bounded corrective turn; a repeat fails visibly.

### Durable model

Add stable IDs and serializable projections for:

- `RoomBriefRevision`: requirements, goal, non-goals, draft/locked state, proposal hash, approval metadata.
- `RegisteredRoot`: harness-issued ID, room membership, canonical worktree top-level, registration source, and current identity metadata.
- `WorkflowSource`: registered root ID, standard/temp kind, relative filename, content hash, `bus-workflow` version, pinned Agentflow profile version, and immutable approved Markdown snapshot.
- `CompiledWorkflow`: canonical node/edge/resource tables, entry and terminal nodes, typed outcomes, bounded cycles, requested capabilities, canonical bytes/hash, and compiler version.
- `PendingWorkflowPromotion`: root/path, prior/new content hashes, compiled-graph hash, diff hash, proposal revision, human approval, and execution receipt.
- `WorkflowProposal`: brief revision, source/profile/compiler/compiled-graph hashes, ordered/dependent to-dos, lanes/isolation groups, requested capabilities, proposed agent launch profiles, completion/escalation rules, proposal hash.
- `WorkflowRun`: approved proposal and stored compiled graph, lifecycle (`approved`, `running`, `needs_human`, `paused`, `completed`, `failed`, `cancelled`), current graph cursor/decision, and event watermark.
- `TodoItem`: summary, dependency IDs, owner, model/effort, state, dispatch/request IDs, blockers, evidence references.
- `Inquiry`: the user's side question, selected owning agent, correlated request/reply, relayed state, and whether the user converted it to a pivot.
- `Handover`: retired and replacement agents, trusted brief/assignment/decision/evidence snapshot, unverified claims, and transfer state.
- `Operation`: deterministic ID, typed parameters/hash, prepared/accepted/completed/uncertain state, and Bus receipt/result.
- `OrchestratorEvent`: version, room/run/turn IDs, monotonic sequence, timestamp, typed payload, and content-size metadata.

Store append-only events below the private Bus data root, partitioned by room, with a compact atomic projection/checkpoint for startup. The journal is the sole authority for orchestrator conversation, brief revisions/locks, proposals, approvals, promotions, operations, inquiries, and recovery; a corrupt tail is detected and truncated only to the last verified complete record while the original bytes are preserved for diagnosis. Never persist streaming deltas or hidden reasoning. Large/binary tool evidence is not copied into the model journal; store a bounded summary, path/reference, size, and digest.

Keep `BusState` authoritative only for rooms, terminal agents, coding-agent messages/delivery, retained/retired terminal metadata, and prompts whose ordered recipients include the orchestrator as a durable inbound queue. Build on Task 0's ordered representation by replacing `AgentRecipients(Vec<AgentId>)` with one in-memory `RoomRecipients(Vec<RoomRecipient>)`, where `RoomRecipient` is `Orchestrator | Agent(AgentId)`; no fake terminal identity or separate boolean can lose mixed-recipient order. Its compatibility codec accepts legacy agent-ID arrays and continues emitting that v1 shape for agent-only state; the first orchestrator recipient requires the v2 tagged sequence. Add a correlation ID to drafts/prompts. The journal idempotently accepts each prompt ID, and a persisted consumption watermark lets startup find every saved-but-unaccepted orchestrator prompt. `BusSnapshot` carries the pending inbox plus a bounded journal-derived orchestrator projection and watermark, never a second writable copy. Continue reading/writing version 1 while no orchestrator-persisted field exists; atomically migrate to version 2 only when such state is first created, preserve every existing field exactly, and document that this is one-way once used. Do not parse arbitrary existing notes into goals; preserve non-empty notes as read-only legacy content in the right panel, never as an editable goal source, and initialize the structured brief empty.

### Provider and context loop

Introduce a small `ModelAdapter` trait and one DeepSeek implementation using `reqwest` with an explicit rustls feature/provider configuration and automatic retries disabled. Prove that dependency choice with `just windows-lint` as soon as it lands and change it before later work if the configured Windows toolchain cannot build it. The first version sends non-streaming Chat Completions to the fixed DeepSeek endpoint with `model: deepseek-flash`, `thinking: { "type": "disabled" }`, `tool_choice: auto`, a conservative output limit, and an opaque hash of the room ID as `user_id`. Reject any unexpected `reasoning_content`; record normalized token usage and finish reason, never raw authorization headers, provider bodies, or hidden reasoning.

One async runtime owns lightweight serialized actors for rooms with configured orchestrators. An actor consumes human turns, agent replies/status changes relevant to its run, timeouts, settings changes, and shutdown. Only one model/tool step mutates one room session at a time. A wait registers a durable wake subscription and ends the step rather than blocking it; newly arriving human input interrupts a model wait where possible and otherwise takes the next bounded turn ahead of agent wakeups. The actor emits data-only commands/results to the existing coordinator, which remains the sole writer of Bus delivery state and terminal snapshots.

Build each provider request from the latest structured checkpoint plus a bounded recent suffix. Authoritative brief/workflow/to-do/decision/operation fields are reloaded verbatim on every turn and are never summarized. Resolved conversational detail may be compacted; terminal/source payloads are excluded. Use byte/token budgets well below the advertised 1M window so context cost grows with active coordination objects rather than repository LOC.

Classify provider failures once. Retry a small bounded number of pre-admission transport, 429, and retryable 5xx failures with cancellable jittered backoff. Accept `stop` only for complete text and `tool_calls` only for complete validated calls; classify `length` as truncation and `content_filter` as policy failure. Treat provider-returned `insufficient_system_resource` and `aborted` as bounded retryable interruptions before any effect. Model local HTTP/backoff cancellation separately as `Cancelled`, with no provider decoding or retry. Unknown finish reasons, unexpected reasoning, authentication, billing, invalid/schema requests, ambiguous effects, and exhausted retries become actionable state. Execute validated tool calls sequentially in source order; never execute a partial or truncated call.

### Workflow, approval, and goal flow

Resolve candidate workflow roots from human registrations and the canonical worktree top-level for each room-agent PWD. Preserve distinct worktrees rather than collapsing them through Git's common directory; de-duplicate only identical canonical paths. Workflow names that appear in multiple roots coalesce only when their content hashes match, otherwise the proposal must name a visible root ID. A rootless room can converse and draft but cannot approve or launch. `list_workflows` and `read_workflow` accept only normalized basenames under `.bus/standard` or `.bus/temp`, regular UTF-8 files under a size cap, and reject symlink/reparse-point escapes.

Define one reviewable file contract instead of a separate diagram and machine manifest. YAML frontmatter carries only `bus-workflow: 1`, name/description, inputs, and global run/replacement/round/token limits. Exactly one fenced `mermaid` block begins with `agentflow-beta` and supplies the control graph. Stable node/flow IDs are execution identities; labels are display text. Official Agentflow shapes and `-->` sequence, `-.-` reference, and `--x` failure edges supply the base vocabulary. Markdown sections provide longer human-readable instructions or references through explicit same-file IDs; all such references must resolve exactly once and remain within the file snapshot.

Compile source through a deterministic pipeline:

```text
workflow Markdown
      |
      v
frontmatter + single Agentflow block + instruction sections
      |
      v
pinned Bus Agentflow parser/profile
      |
      v
canonical CompiledWorkflow + diagnostics + hashes
      |
      v
room-specific proposal/to-dos -> exact human approval -> graph executor
```

Do not embed a JavaScript runtime or implement Mermaid rendering. Implement only the pinned Agentflow source subset needed to build the typed Rust graph, with compatibility fixtures derived from Mermaid `mermaid@12.0.0` (commit `98a0945418c76238f15df2afaddbba4272656c3b`) and its documented semantic model. Record that provenance beside the fixtures. Reject anything outside the profile rather than silently ignoring it. The compiler checks identity uniqueness, reference resolution, reachability, legal fan-out/fan-in, typed and exhaustive decisions, failure paths, finite bounds on every reachable cycle, isolation constraints, capability monotonicity, and launch-profile feasibility. It canonicalizes semantic content independently of display whitespace while retaining the exact source bytes and source hash for review. Any compile error returns source-located diagnostics to the human and, for an orchestrator-authored draft, permits one bounded `workflow-writing` correction before entering `needs_human`.

The binary embeds two non-overridable skills. `workflow-writing` receives the fixed file/profile schema, bounded examples, compile diagnostics, `list_workflows`, `read_workflow`, and `write_temp_workflow`; it can author or revise only `.bus/temp`. `workflow-execution` receives the approved compiled graph and coordination state; it can explain proposals, answer sitrep, route inquiries, and choose only an enumerated recovery edge. Neither skill can register tools, edit the standard library, choose an arbitrary next node, or perform technical work. The deterministic executor advances ordinary ready nodes, waits, joins, evaluates typed outcomes, follows explicit edges, and stops at gates without spending an orchestrator model call. Invoke the model only for initial intent-to-workflow/proposal authoring, direct human conversation, or an exception that the compiled graph marks recoverable.

For a custom request, `workflow-writing` may draft Markdown with `write_temp_workflow`; the executor resolves the selected registered root itself and atomically writes only within `.bus/temp`. Every used temp directory contains a `.gitignore` with `*`; it may be shipped as a tracked repository file or self-ignore when first created so generated workflows do not dirty another checkout. A standard update uses `propose_workflow_promotion` and produces a durable pending projection with an exact root, path, old/new digest, compiled-graph hash, diff hash, and visible diff. Only an exact human UI/control action bound to those values lets the executor perform that one standard write; chat text and model actions cannot approve it.

`propose_run` updates the unlocked Room Brief and supplies a complete graph-derived to-do projection. The UI renders it, and the orchestrator posts a concise approval request in room history. Only the human UI action (or an exact deterministic control command in tests) can append `RunApproved(proposal_hash, compiled_graph_hash)`, lock the brief, and release ready tasks. Natural-language model output cannot self-approve. A side inquiry creates an `Inquiry` and does not alter source/compiled/proposal/run hashes. A requested pivot pauses affected dispatch, recompiles a new proposal revision, preserves completed evidence only where its node identity and input contract still match, and waits for approval.

### Supervision, permission, and handover

Status transitions and deadlines are evidence, not technical judgments. A blocked agent can receive a coordination answer derived from the locked brief/workflow, a routed question to another agent, an allowlisted permission, or escalation. Provider-specific permission recognizers convert a bounded terminal snapshot into a typed request. Approval is valid only if terminal identity and a real monotonic output revision/digest still match; one server-side approve-once handler atomically rechecks identity, revision, digest, action category, and normalized paths before writing a fixed provider response and consuming the operation. Only recognized read/edit/create prompts wholly inside the assigned registered PWD are eligible; commands, network, packages, Git publication/history rewrite, deletion, credentials, hidden/VCS paths, stale, unknown, or out-of-root requests escalate.

Retirement differs from deletion. It requires either exact human approval of the replacement proposal or an unused replacement budget/profile in the approved run. It suspends delivery, never closes a `Working` terminal without an explicit human-approved stop boundary, closes the owned terminal through the guarded identity path only when safe, confirms closure, preserves the `Agent`, requests, replies, assignment, and worktree/PWD evidence, and marks the agent retired. Retired agents are excluded from `All`, direct recipients, sends, and assignment. The handover generator uses only durable orchestration fields and independently verified evidence; the retired agent's own final summary is an explicitly unverified input. A replacement receives the exact handover plus its approved assignment, and ownership changes only after its creation receipt is durable.

The orchestrator may use agent response content to compare recommendations or execute workflow-specified convergence, but it does not adjudicate implementation details from its own source reading. Independent-lane visibility is enforced by the harness: lane bodies/tails remain durable but are withheld from the orchestrator model context, peer prompts, state/tail tools, and wake results until the approved workflow opens a convergence stage. Each harness-generated lane prompt requires a final bounded `LaneOutcome` envelope; Rust parses `complete`, `needs_input`, or `blocked` plus validated evidence references and exposes only that typed result, reply ID, runtime status, and digests to the model. A missing/malformed envelope or any non-complete outcome enters `needs_human` and renders the correlated body directly to the human. Only all-valid `complete` outcomes can open convergence. A side-inquiry reply from an isolated lane follows the same direct human projection without transiting the model. Each dispatch is constructed from the locked brief, approved lane assignment, and lane-permitted evidence.

## Risks and recovery

- Risk: A low-cost model can still hallucinate its role or misclassify a technical question. Mitigation: withhold technical context, require coordination-object summaries or byte-verified agent excerpts, restrict tools, validate every effect in Rust, allow one correction, and fail visibly. Semantic prose detection remains defense-in-depth rather than a claimed hard boundary.
- Risk: Read-only access can still leak secrets to a remote model. Mitigation: expose only bounded high-level outlines/coordination documents, deny hidden/credential/VCS paths and arbitrary source search, disclose remote processing in Settings, cap payloads, and never grant authority based on file contents.
- Risk: API credentials are plaintext at rest in a local file. Mitigation: isolate them from settings/state, use existing private directory/file permissions and atomic/symlink-safe writes, redact memory/debug/log projections, and document that OS-keychain integration is a future hardening option.
- Risk: The journal and terminal Bus state can diverge across a crash, including after a human prompt is saved but before the actor sees it. Mitigation: the journal is the sole accepted-orchestrator authority while Bus owns rooms/terminal agents/coding-agent delivery and the durable prompt inbox; separate documented effect and inbox-acceptance commit orders, prompt-ID deduplication, consumption watermarks, deterministic operation IDs, and startup reconciliation bridge the boundary without duplicate writable copies.
- Risk: Network/model work could stall Bus. Mitigation: a separate cancellable async runtime, bounded channels, per-room serialization, explicit timeouts/backoff, and tests proving the coordinator poll remains responsive.
- Risk: Provider API contracts, TLS features, CLI flags, or model names drift. Mitigation: assert the exact DeepSeek wire name/thinking/finish contract in mock tests, gate the chosen rustls features on Windows as soon as introduced, use a reviewed fail-closed launch capability table, show unsupported combinations in proposals, and provide no arbitrary argument escape hatch.
- Risk: Mermaid Agentflow is new and explicitly beta, while no mature native Rust parser yet targets its version-12 semantic grammar. Mitigation: version Bus workflows independently, pin a deliberately small Agentflow profile, keep checked-in compatibility fixtures derived from the documented Mermaid 12 semantic model, reject unsupported/unknown syntax instead of guessing, and require an explicit compiler/profile migration plus new proposal hash before accepting a later grammar.
- Risk: A model-authored Mermaid graph can be syntactically valid but semantically unsafe, ambiguous, or unbounded. Mitigation: compile into a closed typed Rust graph, promote execution-relevant upstream warnings to errors, reject arbitrary code/tools/connectors/capability expansion, require typed exhaustive branches and finite bounds on every cycle, expose source-located diagnostics, and approve exact source/profile/compiler/compiled-graph hashes.
- Risk: Permission prompt parsing can approve the wrong action after terminal output changes. Mitigation: support only recognized provider fixtures and the narrow in-root read/edit/create allowlist; one server handler atomically rechecks identity, revision/digest, category, and normalized path immediately before its fixed response; escalate every command/network/Git/hidden/credential/unknown/stale/out-of-root request.
- Risk: Temporary workflows dirty repositories, collide across worktrees, or overwrite standard files. Mitigation: use registered canonical worktree roots rather than common Git directories, coalesce only identical hashes, install `.bus/temp` ignore rules, and require an exact human UI/control approval for one root/path/hash-bound atomic promotion.
- Risk: A bad agent's claims poison its replacement. Mitigation: handovers derive from locked orchestration state and independently verified evidence; self-reports stay explicitly unverified and the old transcript/worktree remains available.
- Risk: Right-panel layout regresses the current compact TUI. Mitigation: split only room views above a tested width, use an alternate view when narrow, and retain existing terminal/composer/history geometry tests.
- Risk: Replacing the notes editor can strand existing user-authored notes or reintroduce a second goal writer. Mitigation: preserve non-empty legacy notes verbatim in state and expose them only through a labeled read-only/selectable panel block; empty notes consume no UI, and no legacy-note action mutates the locked brief.
- Risk: A state migration or journal defect strands an active room. Mitigation: keep v1 while unused, migrate atomically and one-way only when orchestrator state is first persisted, refuse unknown/corrupt versions, keep original journal bytes on tail repair, and make disabling the key stop model activity without deleting state.
- Recovery: The entire feature is dormant when no orchestrator key is configured. Clearing the key cancels model calls and returns rooms to existing coding-agent-only behavior while preserving state. A running workflow retains its exact source/profile/compiler/compiled-graph snapshot; a future unsupported Agentflow change cannot mutate it and instead blocks only new compilation. Before first persisted orchestrator use, rollback remains a normal v1 rollback. After the one-way v2 transition, rollback requires an explicit compatible exporter/reader; never claim or attempt an automatic destructive downgrade.
