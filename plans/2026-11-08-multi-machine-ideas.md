# Multi-machine Bus — ideas, not a spec

**状态**：ideas only（未排期、未承诺）
**作者**：dylanliu8949
**创建日期**：2026-11-08

> 这是一份产品想法记录，不是计划、不是规格、不是承诺。它记录我们想让 Bus 在多机环境下长成什么样，以及哪些约束必须在动手前想清楚。单机可靠性是前置条件：多机只会把每个单机故障模式变成永久模式。

## 为什么

单个 Bus 进程在一台机器上已经能协调几十个 agent。下一步是把 Bus 扩到多台机器（复活 herdr 的部分代码），这样一台机器上的房间和能力可以被另一台机器上的开发者/协调者使用。目标不是做分布式系统，而是让"多台机器上的多个房间"看起来像一个 Bus。

## 形态

- 每个 room 只存在于一台机器上。room 是单写者，所以 room 内部不需要共识。
- 通过 SSH 连接机器，不引入外部服务器或消息中间件（沿用 herdr 的做法）。
- 有一个 master 实例：展示所有机器上的所有 room，以及一个供所有 orchestrator 使用的 MASTER room（和今天一样）。
- dashboard 覆盖所有机器，而不是某台机器。

## 身份

- agent 名字在每台机器内唯一即可；跨机器时加上机器名限定（`impl@box-1`）。
- room 同理：room 归属一台机器，全局标识是 `room@machine`。
- request / message id 保持 room 本地：room 单写者，不需要全局计数器，也不存在跨机器撞号。
- 需要跨机器指代的东西，一律用 `name@machine` 形式。

## 放置与通信频率

- 高频边：orchestrator ↔ worker、worker ↔ worker。这也是为什么一个 room 和它的 orchestrator 要放在同一台机器上——把忙的边留在本地。
- 低频边：orchestrator ↔ orchestrator、developer ↔ orchestrator（master 层）。这些边跨机器，开发者接受这部分互联网延迟。
- 如果某个 orchestrator 管的 room 分布在多台机器上，它到远端 room 的边就变成网络边并付出延迟；dashboard 要测量每台机器/每条跨机器边的延迟，让"要不要搬 room"由数据决定，而不是拍脑袋。

## master 与传输

- master 是唯一的聚合者：它通过 SSH 读取每台机器的状态并合并展示。
- master 必须能容忍某台机器不可达：显示为 unreachable / stale，而不是显示为空闲。**down ≠ idle**。
- 跨机器投递必须幂等：SSH 连接断开后重试不能造成重复投递。
- master 上的顺序来自每台机器自己的因果序列，而不是全局时间。

## 时钟与排序

- 多机时间同步用免费开源的外部时间服务（chrony / NTP 一类）。
- 即便如此，也要测量并展示每台机器的 offset，不要假设它是零。
- 跨机器事件永远不用墙上时钟排序；墙上时间只用于展示和延迟计算（并带上 offset 的不确定度）。

## dashboard 作为 sentry

三块内容（已作为单机 dashboard 的目标）：

1. **Messaging**：投递成功率 + 延迟。
2. **Agents**：创建、删除、解阻塞（谁解的、阻塞了多久）。
3. **Errors**：错误计数随时间 + 按次数排序的 top 100（不含堆栈，细节看 `--dev` 日志）。

多机加入的维度：

- 每台机器一行/一个维度：可达性、build sha（版本漂移）、时钟 offset、room 归属（以及归属冲突）、状态是否 stale。
- 指标键保持可组合：`node × provider × room`，不要把单机假设写死。
- `/data` 是可被 agent 读取的契约，sentry 的告警检查（阈值、以及"期望非零却为零"）都应能从它算出来。

## 必须成立的投递语义

- 请求在 turn 结束时落定，而不是等一个可能永远不来的回复。
- 被重启/掉线打断的请求必须确定性地落定，并记录是哪个 generation 关闭了它——这条在单机是"服务器重启"，在多机就是"节点失联"。
- 每条投递在跨机器重试下幂等。
- 启动账本（每个 launch attempt 一个持久结果）要能回答"这个 agent 到底有没有在那台机器上起来"。

## 需要被 sentry 抓到的故障模式

- 节点不可达 / 状态过期。
- 同一 room 被两台机器同时声称（归属冲突）。
- 版本漂移（不同机器跑不同 build）。
- 时钟漂移。
- 跨机器重复投递。
- 阻塞时间异常（orchestrator/developer 没来解）。
- 期望非零却为零的计数器（例如 agent 在跑但 launch 次数为 0、compaction 恒为 0）。

## 开放问题

- 机器失联后，它的 room 是否可以被迁移到别的机器？还是就地等待恢复？
- master 自己挂了怎么办？单 master 足够吗？
- 节点发现与认证：直接读 ssh config，还是显式的机器清单？
- 版本升级策略：允许漂移多久，dashboard 是否阻止/告警？
- 跨机器消息的审计：一条消息在 master 上如何展示它的完整路径？

## 明确暂不做

- 外部消息中间件（Kafka/NATS/Redis 等）。
- 数据库或共享存储。
- 全局共识协议。
- 房间自动再平衡。
