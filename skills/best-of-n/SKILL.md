---
name: best-of-n
description: Converge conflicting proposals that N agents gave for the same technical question into one ranked conclusion — universal (every source independently recommended the same option and it holds up under verification), clear (the first place beats the rest on a named mechanism), or toss-up (the gap is small, but there is still a total order and still a next step) — with a written reason for every eliminated option. The ranking is retained: when the first place fails, the remaining options plus the failure evidence become the seeds of the second round instead of being reinvented. Adjudicates only disputes over technical approaches — triage and deciding what to do next belong to the orchestrator (an orchestrating agent or the developer). Use when several agents have already been fanned out and returned multiple proposals and you are asked to "converge", "pick one", "best of n", "which of these approaches", "they are arguing", or when the first place did not work and you are asked to decide the next step.
---

# Best-of-N

Read the adjudication principles in [guide.md](./guide.md) completely: the scope test, the ranking
criteria, the burden of proof on complexity, the no-blending rule, and why the ranking must be
retained are all there. Without it this skill will treat "synthesizing everyone's opinions" as convergence.

This skill **does not fan out**. The N proposals are produced by the developer (different sessions,
different models, different review lanes); this skill only adjudicates, ranks, and retains — the
independence of those proposals is exactly where their value comes from, and subagents generated by
this skill share the same priors and cannot produce the same disagreement.

## Where the proposals come from: Bus (cross-model fan-out)

Bus can send the same question to claude / codex / cursor agents at the same time, and is currently
the only cross-model fan-out channel. Bus is this repository: `./run dev` builds and starts the
interactive instance, and control commands go through `./run dev-control COMMAND`. Control
commands only connect to an **already running** instance and will not start one for you —
the interactive UI must be started by the developer in a terminal they keep open.

```sh
# Key: control commands must use the same BUS_DATA_DIR as the running instance, otherwise they cannot connect.
#   Without BUS_DATA_DIR, control commands attach to the last opened session under ~/.local/share/bus;
#   an instance started with BUS_DATA_DIR (e.g. ~/.bus-rv) is only reachable with the same value, and
#   `./run dev-control state` otherwise returns control_unavailable.
#   Read the instance's real value with `ps eww -p <pid> | tr ' ' '\n' | grep BUS_DATA_DIR`.
export BUS_DATA_DIR=/absolute/path/matching/the/running/instance
cd "<bus repository root>"         # control commands go through ./run dev-control COMMAND; do not call bus directly

./run dev-control state            # first see which rooms and agents exist; reuse existing ones, do not create duplicates
room=$(./run dev-control room create "<topic>" | jq -r '.result.room_id')
a1=$(./run dev-control agent add --room "$room" --name claude-x --provider claude --pwd "<worktree>" | jq -r '.result.agent_id')
a2=$(./run dev-control agent add --room "$room" --name codex-x  --provider codex  --pwd "<worktree>" | jq -r '.result.agent_id')
a3=$(./run dev-control agent add --room "$room" --name cursor-x --provider cursor --pwd "<worktree>" | jq -r '.result.agent_id')

# One message to all recipients yields one shared message_id; --file can be repeated to attach evidence
msg=$(./run dev-control send --room "$room" --to "$a1,$a2,$a3" --text "<brief>" | jq -r '.result.message_id')
./run dev-control wait --message "$msg" --timeout 600
./run dev-control history --room "$room"   # raw Markdown replies, i.e. this skill's --input
```

- `send` only proves the message was persisted and queued; it **does not mean the agent started or
  replied**. The settlement signal is `complete: true` from `wait` or `message status`. A terminal
  that looks idle does not count.
- The brief must state clearly: the locked goal, what the dispute is, a request for **one** approach
  plus its cost, and **do not touch the repository**. They run concurrently on the same worktree; any
  one of them writing files pollutes the current state the other agents see.
- Each agent's reply is one `--input`. The source identity (provider + agent name) goes into the
  record, but per the guide it does not take part in the ranking — the same approach proposed by two
  providers is one option with two sources, not two votes.

```text
INPUT $ARGUMENTS =
  [--input <file>]...        one file per proposal; a single file containing several is also accepted, split by main
  [--goal <one-line>]        locked goal; when omitted, discover it in the order below
  [--dispute <id>]           adjudicate only this one
  next [--dispute <id>] [--failed <option-id>]   switch: read the next place from the existing record

branch_slug = the current branch name with every character outside [A-Za-z0-9_-] replaced by `-` (detached uses `_detached_`)
ledger      = temp/best-of-n/<branch_slug>/ledger.json
rendered    = temp/best-of-n/<branch_slug>/decisions.md

========== 0. Switch path (`next`) ==========

IF $ARGUMENTS starts with `next`:
  Run:
    python3 skills/best-of-n/scripts/best_of_n.py next \
      --ledger <ledger> --dispute <id> --failed <option-id>

  It prints **all** surviving options not yet attempted (each with TLDR and cost), the failure
  criterion, the attempts already recorded, and why the first place won in the first place.
  They are the seeds of the second round, not a queue waiting to be popped —
  the first failure is itself new evidence and may reorder them.
  Per the guide's "When switching to the next place", judge whether that reason has been overturned by this failure:
    - Overturned → execute the next place, and append this failure to the record:
      `python3 skills/best-of-n/scripts/best_of_n.py attempt --ledger <ledger> \
         --dispute <id> --option <failed option-id> --outcome "<what happened>"`
      The record is written by `attempt`, not `record` — `record` only validates and renders and does not change the ledger.
      Skip this step and the next `next` will recommend an option that already failed as a seed again.
    - Not overturned → STOP. The root cause of the failure is not a wrong choice of approach; go back to
      the problem itself and gather evidence again, do not slide down the ranking.
  Then finish; do not re-adjudicate the other disputes.

========== 1. Lock the goal ==========

Take the goal from the first available source in this order, stop as soon as one is found, never merge several sources:
  1. the verbatim `--goal`;
  2. the full `## 目标` section of the associated plan;
  3. `temp/review-pr/<branch_slug>/.locked-goal` (written by the `pr` skill);
  4. ask the developer for one sentence.

IF none is available
  STOP and ask. **Do not** infer the goal from the diff, commits, the PR description, or the N
  proposals themselves — those proposals are exactly what the goal adjudicates, and using them to
  derive the goal lets the contestants define the finish line.

The goal and the locked non-goals are this round's locked inputs: do not rewrite, expand, or overturn them.

========== 2. Normalize: extract disputes and options from the N proposals ==========

Read every `--input` completely. Record the source identity of each (lane / model / author side or
reviewer side); it goes into the record but **does not affect the ranking** — the ranking looks only
at the approach itself, not at who proposed it, and is not weighted by how many proposed it.
Two agents proposing the same approach is one option with two sources, not two votes.

FOR EACH dispute:
  Write a one-sentence **technical question** (not some agent's position).
  Check once against that sentence that it really is a technical dispute — the orchestrator already
  judged so; this is only a backstop:
    If all N proposals were implemented, would the resulting code differ?
      Yes → continue.
      No  → it is about timing, order, or ownership. Hand it back to the orchestrator, keep it out of
            the ledger, and do not decide where it should go yourself.

  Collect every **distinct** approach as an option, each with:
    - `tldr`: one or two sentences on **what it proposes to do** (not its reasons, not its benefits)
    - `sources`: the sources that proposed it
    - `cost`: what it introduces — new concepts, files, abstractions, branches, state
  Different wordings of the same approach merge into one option, with `sources` accumulated.

  **Every submitted approach must become an option**, including obvious losers: dropping it drops a future fallback.

  When the only dispute a participant had an opinion on was handed back to the orchestrator per a0,
  and so has no option in the record, write them into the top-level `deferred_sources`. **Do not**
  delete them from `sources` — `sources` is the denominator of universal, and deleting a real
  participant launders "2 of 3 recommended" into "everyone gave the same proposal".

========== 3. Adjudicate ==========

FOR EACH technical dispute:
  a0. **First confirm this one is yours to adjudicate**: when the disagreement is really about
      scheduling, PR splitting, what goes first, or a product trade-off, hand it back to the
      orchestrator as is and let it decide where it goes; do not triage for it, do not force a
      ranking, keep it out of the ledger.
      Otherwise continue with a–f. **Do not refuse to rank because it is hard** — a ranking can
      always be produced; when you cannot separate them, judge toss-up, do not refuse a conclusion.

  a. **Eligibility** (binary). For each option, judge whether it fails the goal, hits a non-goal,
     violates a hard rule in `docs/guides/architecture-principles.md`, or requires overturning an
     archived decision. A hit means `disqualified`, stating which one it hit; a disqualification without a reason is invalid.

  b. **Rank** the survivors, total order, no ties, by the guide's simplest → most direct → most likely to succeed.

  c. **Burden of proof on complexity**: by default the first place is the simplest one. To make it
     lose, `beats_runner_up` must name a concrete failure mechanism (which input / timing / platform /
     which line). If you cannot write a mechanism, there is no reason not to choose it — "might not be
     robust enough" and "more extensible" are not mechanisms.

  d. **No blending**: by default adopt one option whole. A third approach absent from the original
     proposals is only allowed when it is simpler than every option it borrows from, and it enters
     a–c as a new option with no exemption.

  e. Write `failure_trigger`: **what counts as the first place failing**. It must be observable —
     some test goes red, some behavior does not appear, some constraint cannot be held. Without it,
     the moment to fall back becomes a subjective judgment.

  f. Set `verdict` (the guide's "Three conclusions"), one of three, by a mechanical test:
       universal —— the chosen option was independently recommended by **every** source, **and it is the only surviving option**;
                    if anyone proposed something else (even ranked second), it is not "everyone gave the same proposal";
       clear     —— you can write, for the first place, a `beats_runner_up` that names a concrete failure mechanism;
       toss-up   —— you cannot write that mechanism. **Rank anyway** (even if nearly arbitrary),
                    and write `toss_up_reason`: what evidence is still missing to separate them.
     Judging clear without a mechanism is passing confidence off as evidence; refusing to rank when
     you cannot separate them leaves the work stalled.
     **What to do next is not yours to decide** — running a spike, choosing by another constraint, or
     asking a human is decided by the orchestrator based on `toss_up_reason`.

Adjudication belongs only to main. Delegated evidence gathering answers local facts only, with no ranking and no decision.

========== 4. Persist ==========

Write the adjudication as `<ledger>` (schema in the `--help` of scripts/best_of_n.py), then:

  python3 skills/best-of-n/scripts/best_of_n.py record \
    --ledger <ledger> --output <rendered>

Everything it blocks has the same shape — **looks done, but no decision was actually made**: tied or
gapped ranks, disqualifications without reasons, a missing failure trigger, silently dropped options,
an adjudicator choosing their own option without saying where the simpler rival loses.
The individual criteria are not copied here: `validate`'s error messages themselves state what is
missing and why it is needed, and the same yardstick written in two places inevitably drifts — this
list had already fallen out of sync with the implementation in the previous round.

IF the script exits non-zero: fix the ledger per the error messages and rerun; do not hand-write
`<rendered>`, and do not delete an option to pass validation — the whole point of the ranking is that
there is an examined fallback when the first place fails.

========== 5. Output ==========

Read(<rendered>) and present it verbatim; do not rewrite, reorder, or add conclusions. After it, in a separate paragraph, give:

  - the disputes handed back to the orchestrator, one by one (scheduling / PR splitting / product
    trade-off / needs a spike first), stating why they are not yours to adjudicate — they were not
    adjudicated, do not let them look resolved;
  - "Decision premise challenge" (if any): when new evidence overturns the factual premise of an
    archived decision, one sentence to the developer;
  - the ledger path, and the switch commands:
    `python3 skills/best-of-n/scripts/best_of_n.py attempt --ledger <ledger> --dispute <id> --option <id> --outcome "<what happened>"`
    `python3 skills/best-of-n/scripts/best_of_n.py next --ledger <ledger> --dispute <id> --failed <option-id>`

STOP. Whether to execute the first place is the developer's decision; this skill changes no production files and performs no Git operations.
```
